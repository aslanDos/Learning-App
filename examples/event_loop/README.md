# Event Loop в Dart

Запускай из корня проекта. Для этих примеров не нужен эмулятор.

## 1. Синхронный код, микрозадачи и события

```sh
dart run examples/event_loop/queues_demo.dart
```

Ожидаемый вывод:

```text
1. Начало main
2. Конец main
3. Первая микрозадача
4. Вторая микрозадача
5. Первое событие
6. Микрозадача из первого события
7. Второе событие
```

Сначала текущий синхронный код выполняется до конца. Затем обрабатываются
микрозадачи. После них выполняется одно событие, затем снова проверяются
микрозадачи. Поэтому строка 6 появляется перед строкой 7.

`Future(() { ... })` планирует переданную функцию как событие.
`scheduleMicrotask` и `Future.microtask` планируют микрозадачи.
Слово «микро» означает категорию планирования, а не небольшую длительность работы.
Микрозадача не прерывает уже выполняющийся синхронный код.

## 2. await приостанавливает функцию

```sh
dart run examples/event_loop/await_demo.dart
```

Ожидаемый вывод:

```text
1. Начало main
2. loadName: до await
3. main продолжает работу
4. Другое событие во время ожидания
5. loadName: после await
6. Получено имя: Алия
```

`Future<String>` представляет результат, который будет строкой, либо ошибку.
`Future<void>` обозначает завершение без полезного значения.

Вызов `loadName()` сразу выполняет начало функции до первого await.
На await выполнение этой функции приостанавливается, и вызывающий код
получает Future. Поэтому main успевает вывести строку 3.

Затем main тоже приостанавливается на своём await. Пока обе функции ждут,
Event Loop может обработать другое событие — строку 4.
Когда задержка завершается, продолжается loadName, а после получения
результата продолжается main.

Здесь задержка 50 мс имитирует ожидание данных. Это не настоящий сетевой запрос.
Она не гарантирует возобновление ровно через 50 мс: занятый isolate может
обработать завершение позже. async и await сами по себе не создают другой поток.

## 3. Синхронная блокировка задерживает даже готовые события

```sh
dart run examples/event_loop/blocking_demo.dart
```

Ожидаемый вывод:

```text
1. Планируем таймер без задержки
2. Блокируем текущий isolate на 200 мс
3. Синхронная работа закончилась
4. Таймер получил возможность выполниться
```

`Timer.run` откладывает функцию как событие без заданной задержки.
Но событие не может прервать текущий код. `sleep` блокирует текущий isolate,
поэтому таймер срабатывает только после строки 3.
Долгое синхронное вычисление так же не даёт обрабатывать другие события.
sleep используется здесь только для демонстрации блокировки.

## Связь с Flutter

Isolate — отдельная среда выполнения Dart со своей памятью и Event Loop.
В главном isolate Flutter выполняются обработчики действий пользователя
и работа framework над кадрами, включая Build, Layout и Paint.
Поэтому долгий синхронный код мешает своевременно обрабатывать интерфейс.
Сам движок Flutter также использует другие потоки: весь Flutter не сводится
к одному isolate.

`setState` выполняет переданную функцию сразу и помечает элемент для Build.
Он не показывает новый кадр прямо внутри своего вызова.
Если после setState выполнять тяжёлый синхронный код, обновление экрана
будет задержано. Оборачивание вычисления в Future лишь откладывает его:
после старта оно всё равно занимает текущий isolate.

## Учебная модель и её границы

```text
Текущий синхронный код
         ↓
Все ожидающие микрозадачи
         ↓
Одно готовое событие
         ↓
Снова все ожидающие микрозадачи
         ↓
Следующее готовое событие
```

Очереди хранят отложенную работу, а не выполняют её параллельно.
Синхронные вызовы функций можно представлять как стек вызовов:
main вызывает функцию, функция возвращается, main продолжается.
Стек — не третья очередь.

Future — объект результата, а не очередь и не отдельный поток.
Не все его конструкторы планируют работу одинаково: например,
Future.sync вызывает переданную функцию сразу.
Продолжения await и then связаны с механизмом Future; не стоит считать,
что каждый then обязательно создаёт отдельное событие или микрозадачу.
Бесконечное добавление микрозадач может не дать событиям выполниться.
